# ClubHub - Security Review & Hardening Audit (Phase 11)

This document provides a comprehensive security review of the ClubHub operations portal across the PHP/MySQL core application, the React frontend widget, and the Django analytical reporting module.

---

## 1. Executive Summary & Security Posture

ClubHub was designed following defensive development best practices to prevent common web application vulnerabilities (OWASP Top 10):
- **Zero SQL Injection**: 100% of dynamic database queries use PDO parameterized prepared statements.
- **Cross-Site Scripting (XSS) Prevention**: All dynamic output in HTML templates is encoded via `htmlspecialchars()` (`e()` / `sanitize()`) using `ENT_QUOTES` and `UTF-8`.
- **Cross-Site Request Forgery (CSRF) Mitigation**: All state-changing POST forms and AJAX actions require a cryptographically secure token validated using constant-time `hash_equals()`.
- **Insecure File Upload Protection**: Receipt uploads strictly enforce extension whitelisting, binary MIME-type verification via `finfo_file()`, file size caps (max 2 MB), randomized file renaming, and server-level execution disabling.
- **Role-Based Access Control (RBAC)**: Centralized authorization gates (`require_role()`, `require_login()`) enforce role hierarchy on all protected controllers, forms, and actions.
- **Defensive Server Hardening**: Apache `.htaccess` directives block direct web access to internal directories (`config/`, `includes/`, `logs/`, `sql/`), disable directory listing, and deny script execution in `uploads/`.
- **Least-Privilege Principle**: The Django reporting module operates under an isolated read-only MySQL user (`clubhub_reader`) with unmanaged models (`managed = False`).

## 2. Detailed Vulnerability Audit & Fixes

### A. SQL Injection (SQLi) Audit
- **Risk Assessed**: Attackers manipulating user input to alter database queries, dump credentials, or bypass authentication.
- **Audit Findings**:
  - All database queries across `pages/`, `api/`, `includes/`, and `config/` were reviewed.
  - No dynamic SQL queries concatenate user input directly into query strings.
  - Search filters in `pages/events.php`, `pages/clubs.php`, and `api/search_events.php` properly use `?` parameter placeholders with arrays passed to `PDOStatement::execute()`.
  - Pagination, ID lookups, and foreign key references strictly cast inputs to integers (`(int)$_GET['id']`).
- **Resolution / Status**: **SECURE**. All queries use PDO prepared statements.

---

### B. Cross-Site Scripting (XSS) Audit
- **Risk Assessed**: Injection of malicious JavaScript via user-controlled inputs (e.g. event descriptions, club announcements, remarks, user names).
- **Audit Findings**:
  - The shared helper function `e($string)` wraps `htmlspecialchars($string, ENT_QUOTES, 'UTF-8')`.
  - Multi-line user text (e.g., event descriptions, announcements) uses `nl2br(e($data))`—ensuring HTML escaping runs *before* inserting `<br>` tags.
  - Search keyword input values reflected in form fields use `value="<?php echo e($search); ?>"`.
  - In `assets/js/ajax.js`, dynamic DOM insertions from JSON responses pass strings through `escapeHtml()` to neutralize `<`, `>`, `&`, `"`, and `'`.
- **Resolution / Status**: **SECURE**. No unescaped user reflections identified.

---

### C. Cross-Site Request Forgery (CSRF) Audit
- **Risk Assessed**: Unauthorized transmission of commands from a user that the web application trusts.
- **Audit Findings**:
  - `generate_csrf_token()` produces 64-character hexadecimal tokens generated by `bin2hex(random_bytes(32))`.
  - `verify_csrf_token()` compares tokens using `hash_equals()` to prevent timing attacks.
  - Every POST form in the application embeds `<?php echo csrf_field(); ?>`.
  - The AJAX RSVP endpoint (`api/rsvp.php`) accepts CSRF tokens via either the `X-CSRF-Token` HTTP header or the POST payload.
  - Added short alias function `csrf_token()` in `includes/functions.php` to ensure consistent helper resolution across all modules.
- **Resolution / Status**: **SECURE**. All state-modifying endpoints enforce CSRF validation.

---

### D. File Upload Security Audit (`pages/expense-form.php`)
- **Risk Assessed**: Malicious actors uploading PHP webshells, oversized files, or polyglot files disguised as images.
- **Multi-Layer Defensive Mitigations Implemented**:
  1. **Strict Extension Whitelist**: Only `.jpg`, `.jpeg`, `.png`, `.webp`, `.gif`, and `.pdf` are permitted.
  2. **Magic Byte / MIME-Type Verification**: File contents are inspected with `finfo_open(FILEINFO_MIME_TYPE)` and `finfo_file()`, rather than trusting the user-supplied `$_FILES['...']['type']`.
  3. **Size Limitation**: Uploads larger than 2,097,152 bytes (2 MB) are immediately rejected.
  4. **Collision-Resistant Renaming**: Files are renamed on disk to `receipt_<timestamp>_<hex>.ext` using `bin2hex(random_bytes(6))`, completely stripping user-supplied filenames and preventing path traversal attacks (`../`).
  5. **Directory Script Execution Lockdown**: An `.htaccess` file was placed inside `uploads/` with `Options -Indexes -ExecCGI` and `<FilesMatch>` denying execution of any script extensions (`.php`, `.phtml`, `.cgi`, `.py`, `.sh`, `.exe`).
- **Resolution / Status**: **SECURE**. Defense-in-depth upload validation applied.

---

### E. Access Control & Broken Object Level Authorization (BOLA)
- **Risk Assessed**: Users accessing unauthorized endpoints or editing resources belonging to other clubs by guessing IDs in the URL.
- **Audit Findings & Mitigations**:
  - `require_role()` in `includes/auth.php` guards all administrative and club-head controllers (`club-form.php`, `event-form.php`, `venue-form.php`, `budget-form.php`, `expense-form.php`, `announcement-form.php`).
  - Club heads can only edit clubs where `head_id === current_user_id`.
  - Club heads can only log expenses and submit budget requests for clubs they lead (`pages/expense-form.php` and `pages/budget-form.php`).
  - Only administrators can delete clubs, venues, or approve budget allocations (`pages/budget-action.php`).
  - Only administrators can approve or reject event proposals (`pages/event-action.php`).
  - User registration (`pages/register.php`) forces the role to `'member'`, preventing privilege escalation during sign-up.
- **Resolution / Status**: **SECURE**. Server-side authorization checks verified across all actions.

---

### F. Session Management & Authentication Security
- **Risk Assessed**: Session fixation, credential credential leakage, or plaintext password storage.
- **Audit Findings & Mitigations**:
  - Passwords are hashed using PHP's native `password_hash($password, PASSWORD_DEFAULT)` utilizing the bcrypt algorithm.
  - Password verification uses `password_verify()`.
  - Upon successful authentication in `pages/login.php`, `session_regenerate_id(true)` is immediately invoked, invalidating the previous session ID and preventing session fixation attacks.
  - Sessions are terminated cleanly in `pages/logout.php` via `session_unset()`, `session_destroy()`, and clearing the session cookie.
- **Resolution / Status**: **SECURE**. Session lifecycle adheres to security standards.

---

### G. Server Hardening & Directory Access (`.htaccess`)
- **Risk Assessed**: Direct browser access to sensitive configuration files (`config/db.php`), internal helper functions (`includes/`), database scripts (`sql/`), or error logs (`logs/error.log`).
- **Fixes Applied**:
  - Created master `.htaccess` in the project root:
    - `Options -Indexes` disables directory indexing.
    - `RewriteRule ^(config|includes|logs|sql|\.git)` blocks direct web access with `403 Forbidden`.
    - Restricts access to sensitive file extensions (`.log`, `.sql`, `.env`, `.bak`, `.conf`).
    - Added security headers: `X-Content-Type-Options: nosniff`, `X-Frame-Options: SAMEORIGIN`, `X-XSS-Protection: 1; mode=block`, and `Referrer-Policy: strict-origin-when-cross-origin`.
  - Added secondary `.htaccess` files inside `config/`, `includes/`, and `logs/` denying all web requests (`Require all denied`).
- **Resolution / Status**: **SECURE**. Direct folder access blocked.

---

### H. Information Disclosure & Error Handling
- **Risk Assessed**: PHP displaying call stacks, database error messages, or server paths on fatal exceptions.
- **Audit Findings**:
  - `ini_set('display_errors', '0')` is enforced in `includes/functions.php`.
  - Global `set_exception_handler()` and `set_error_handler()` intercept unhandled errors.
  - Fatal errors log diagnostic context to `logs/error.log` and redirect visitors to `pages/error.php`.
  - The custom error page displays a friendly, non-technical notification without revealing system internals.
- **Resolution / Status**: **SECURE**. Sensitive technical errors are suppressed from visitors.

---

### I. Read-Only Database Separation (Django Reports)
- **Risk Assessed**: Secondary analytical reporting module writing to, altering, or dropping existing PHP tables.
- **Audit Findings**:
  - Dedicated MySQL user `clubhub_reader` configured with `GRANT SELECT ON clubhub.*`.
  - Tested: Any attempted write operations (`INSERT`, `UPDATE`, `DROP`) via `clubhub_reader` are rejected by MySQL with `ERROR 1142: command denied`.
  - All Django models in `django-reports/reports/models.py` explicitly declare `managed = False`.
- **Resolution / Status**: **SECURE**. Isolation and read-only enforcement verified.
